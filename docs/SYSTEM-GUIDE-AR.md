## 1. نظرة عامة — إيه النظام ده

نظام رواتب لمستخدم إداري واحد (Single Admin). الفكرة ببساطة:

**المدير بيسجّل البيانات الثابتة مرة واحدة (أقسام، درجات وظيفية، موظفين، نسب حوافز وخصومات)، وبعدين كل شهر بيسجّل أيام الغياب، وبضغطة زرار النظام بيولّد مسير رواتب الشهر لكل الموظفين، بيراجعه، وبيعتمده. بعد الاعتماد المسير يتقفل ومايتغيرش أبداً.**

النظام مقسوم لستة أقسام رئيسية (نفس تقسيم المواصفات):

| القسم | المهمة |
|---|---|
| إدارة الموظفين | إضافة/تعديل/عرض/حذف بيانات الموظفين |
| إدارة المرتبات | الراتب الأساسي لكل درجة وظيفية (أولى / ثانية / ثالثة) |
| إدارة الأقسام | إضافة/تعديل/حذف/عرض الأقسام + نسبة حافز كل قسم |
| إدارة الحوافز | حوافز القسم + حوافز سنوات الخدمة |
| إدارة الحضور والانصراف | تسجيل أيام الغياب وأثرها على الراتب |
| إدارة التقارير | أربعة تقارير (حضور، حوافز وخصومات، عاملين، مرتبات) |

### الفكرة اللي بيقوم عليها النظام كله

الراتب مش رقم ثابت في جدول الموظف. الراتب **مُحتسَب** من أربع مكوّنات:

```
صافي الراتب  =  الراتب الأساسي (من الدرجة الوظيفية)
              + حافز القسم (نسبة % مرتبطة بالقسم)
              + حافز سنوات الخدمة (نسبة % حسب مدة العمل)
              ± تسوية الحضور (حافز لو مافيش غياب، خصم لو في غياب)
```

يعني لو غيّرت نسبة حافز قسم "المبيعات" النهاردة، ده بيأثر على **مسير الشهر الجاي** — مش على الشهور اللي فاتت. ده مقصود، وهو أهم قرار تصميمي في النظام (اقرأ [القسم 3](#3-المفهوم-الأساسي-اللقطة-الشهرية-snapshot)).

## 2. المعمارية والتقنيات

### الباك إند — `PayRollApi` (ASP.NET Core، Clean Architecture)

```
Domain          الكيانات (Entities) + الـ Enums + محرك الحساب PayrollCalculator
                (كود صافي، مالوش أي علاقة بـ EF Core أو قاعدة البيانات، ومغطى بالاختبارات بالكامل)

Application     الـ DTOs، واجهات الخدمات وتنفيذها، قواعد التحقق (FluentValidation)،
                AutoMapper، واجهات الـ Repositories، التخزين المؤقت (Caching)

Infrastructure  EF Core DbContext + إعدادات الجداول + الـ Migrations + تنفيذ الـ Repositories
                + خدمات JWT/تشفير كلمات المرور + الـ Seeders + توليد PDF (RDLC)

PayRollApi      طبقة الـ Web API — الـ Controllers، Program.cs، الإعدادات

*.UnitTests     مشروع اختبارات لكل طبقة (Domain / Application / Infrastructure / API)
```

**ليه التقسيم ده مهم عملياً؟** لأن منطق حساب الراتب موجود في `Domain` وحده، من غير أي اعتماد على قاعدة بيانات. فتقدر تختبر كل حالات الحساب بالاختبارات الوحدوية من غير ما تشغّل سيرفر أو داتابيز — وده فعلاً موجود في `Domain.UnitTests`.

**التقنيات:**
- .NET / ASP.NET Core Web API
- EF Core + SQL Server (سكيمتين: `payroll` للرواتب و `security` للأمان)
- FluentValidation للتحقق من المدخلات
- AutoMapper للتحويل بين الكيانات والـ DTOs
- JWT للـ Access Token + Refresh Token بنظام تدوير
- `IMemoryCache` للتخزين المؤقت للقوائم
- RDLC لتوليد تقارير PDF
- تعدد اللغات عبر ملفات `.resx` (عربي/إنجليزي) لرسائل الـ API

### الواجهة — `payroll-web` (Angular، Standalone)

- Angular standalone components، من غير NgModules
- **Signals** لإدارة الحالة في كل الشاشات (مش RxJS Subjects)
- Lazy loading لكل مسار (`loadComponent`)
- **AG Grid** لكل الجداول (فرز، تغيير عرض الأعمدة، تعديل داخل الخلية، دعم RTL)
- **ApexCharts** للرسم البياني في لوحة التحكم
- `@ngx-translate` — عربي/إنجليزي، والعربي هو الافتراضي مع `dir="rtl"`
- CSS عادي (مافيش Material أو Tailwind) بثيم إداري بسيط

> ملاحظة: فيه مجلد شقيق اسمه `PayRollAngular/` — ده هيكل قديم غير مستخدم إطلاقاً، آمن حذفه. الواجهة الفعلية هي `payroll-web` فقط.

### إزاي الاتنين بيتكلموا مع بعض

```
المتصفح  →  payroll-web (localhost:4200)
              │  كل النداءات على /api  (نفس الأصل same-origin)
              ▼
         proxy.conf.json  →  https://localhost:7290  (الـ API)
```

**الـ Proxy في بيئة التطوير إجباري مش اختياري.** لأن كوكي الـ Refresh مضبوط على `SameSite=Strict`، فلو الواجهة نادت `https://localhost:7290` مباشرة من `http://localhost:4200` المتصفح هيرمي الكوكي بصمت وتسجيل الدخول هيفضل يفشل بعد أول 15 دقيقة من غير رسالة خطأ واضحة.

## 3. المفهوم الأساسي: اللقطة الشهرية (Snapshot)

ده أهم مفهوم في النظام كله، ولو فهمته هتفهم باقي القرارات.

**المشكلة:** لو النظام بيحسب الراتب لحظياً من الإعدادات الحالية، فلما المدير يزوّد نسبة حافز قسم من 10% لـ 15% في شهر مارس، هتلاقي تقرير شهر يناير اتغيّر كمان. وده كارثة محاسبية.

**الحل المُطبَّق:** لما تولّد مسير شهر، النظام **بينسخ كل القيم المستخدمة** في جدول `PayrollItems` — مش بس المبالغ، لكن كمان:
- الراتب الأساسي وقتها
- نسبة حافز القسم وقتها
- نسبة حافز الخدمة وعدد سنوات الخدمة وقتها
- عدد أيام الغياب ونسبة التسوية ونوعها
- **حتى اسم الموظف واسم القسم واسم الدرجة** وقتها

فلو الموظف اتنقل قسم بعد كده، أو اتغيّر اسم القسم، أو اتحذف الموظف — مسير يناير يفضل زي ما هو بالحرف.

**نتيجتين مهمتين:**
1. التقارير بتقرأ الصفوف الجاهزة من `PayrollItems` — مش بتعيد الحساب. فسريعة ومستقرة.
2. صفوف `PayrollItems` **تُكتب مرة واحدة** — إعادة التوليد بتمسح كل الصفوف وتعيد إنشاءها، ومابتعدّلش صف موجود.

## 4. محرك احتساب الراتب — قلب النظام

الملف: `Domain/Services/Payroll/PayrollCalculator.cs` ومعاه استراتيجيتين.

### 4.1 المدخلات لكل موظف

| المدخل | مصدره |
|---|---|
| الراتب الأساسي | `JobGrades.BaseSalary` حسب درجة الموظف |
| نسبة حافز القسم | `Departments.IncentivePercent` حسب قسم الموظف |
| نسبة حافز الخدمة | من `ServiceIncentiveTiers` حسب تاريخ التعيين |
| نوع ونسبة تسوية الحضور | من `AttendanceRules` حسب عدد أيام الغياب في الشهر |

### 4.2 إزاي بتتحدد نسبة حافز سنوات الخدمة

`Domain/Services/Payroll/ServiceIncentiveTierResolver.cs`

```
النسبة = أعلى شريحة تتحقق فيها الشرط:
         نهاية فترة الشهر  >  تاريخ التعيين + (MinYearsExceeded سنة)
```

ثلاث نقاط حاسمة:
- **المقارنة "أكبر من" وليست "أكبر من أو يساوي"** — يعني موظف عيّن في 2020-01-01، في مسير شهر 2025-01 (نهايته 2025-01-31)، تاريخ `2020-01-01 + 5 سنوات = 2025-01-01`، و `2025-01-31 > 2025-01-01` ✔ فيستحق شريحة الـ 5 سنوات. لكن في مسير 2024-12 (نهايته 2024-12-31) مايستحقش. ده مطابق لصياغة "من **تجاوز** 5 سنوات".
- **الشرائح لا تتراكم** — الموظف اللي عنده 8 سنوات بياخد شريحة الـ 7 سنوات (10%) فقط، مش 5% + 10%. أعلى شريحة مطابقة تفوز وبس.
- **مافيش شريحة مطابقة = صفر بالمية**، مش خطأ.

### 4.3 إزاي بتتحدد تسوية الحضور

`Domain/Services/Payroll/AttendanceRuleResolver.cs`

```
القاعدة المختارة = أول قاعدة تحقّق:  FromDays ≤ أيام الغياب ≤ (ToDays أو ما لا نهاية)
```
لو مافيش قاعدة مطابقة → **لا حافز ولا خصم** (صفر).

### 4.4 طريقتا الاحتساب

النظام بيدعم طريقتين قابلتين للتبديل من شاشة الإعدادات، والطريقة المُستخدمة بتتسجّل داخل المسير نفسه.

#### (أ) الطريقة الجمعية — Additive (الافتراضية)

كل نسبة بتتطبّق على **الراتب الأساسي** بشكل مستقل:

```
حافز القسم   = الأساسي × نسبة القسم
حافز الخدمة  = الأساسي × نسبة الخدمة
تسوية الحضور = ± الأساسي × نسبة الحضور
─────────────────────────────────────
الصافي = الأساسي + حافز القسم + حافز الخدمة + تسوية الحضور
```

#### (ب) الطريقة التراكمية — Compound

ترتيب ثابت: قسم ← خدمة ← حضور، وكل خطوة بتتطبّق على **الإجمالي الجاري**:

```
ر1 = الأساسي
حافز القسم   = ر1 × نسبة القسم       ←  ر2 = ر1 + حافز القسم
حافز الخدمة  = ر2 × نسبة الخدمة      ←  ر3 = ر2 + حافز الخدمة
تسوية الحضور = ± ر3 × نسبة الحضور
─────────────────────────────────────
الصافي = ر3 + تسوية الحضور
```

الترتيب ده **ثابت وغير قابل للتعديل** من الواجهة.

### 4.5 مثال محسوب بالكامل

موظف: راتب أساسي 10,000 — حافز قسم 10% — حافز خدمة 5% — خصم حضور 5%

| الطريقة | حافز القسم | حافز الخدمة | تسوية الحضور | **الصافي** |
|---|---|---|---|---|
| جمعية (Additive) | 1,000.00 | 500.00 | −500.00 | **11,000.00** |
| تراكمية (Compound) | 1,000.00 | 550.00 | −577.50 | **10,972.50** |

شرح التراكمية خطوة بخطوة:
- ر1 = 10,000 → حافز القسم = 10,000 × 10% = **1,000** → ر2 = 11,000
- حافز الخدمة = 11,000 × 5% = **550** → ر3 = 11,550
- خصم الحضور = 11,550 × 5% = **577.50** (بالسالب)
- الصافي = 11,550 − 577.50 = **10,972.50**

### 4.6 قواعد التقريب والحدود

- كل مبلغ بيتقرّب لخانتين عشريتين بـ `MidpointRounding.AwayFromZero` **عند الخطوة اللي اتحسب فيها** — مش في النهاية. يعني `0.125` تبقى `0.13` مش `0.12`.
- **الصافي لا ينزل تحت الصفر أبداً** — لو الحساب طلع سالب بيتثبّت على صفر، والنظام بيسجّل تحذير في الـ Log باسم الموظف والشهر. ده مفروض مايحصلش بنسب صحيحة، فوجود التحذير ده في الـ Logs معناه فيه إعداد نسب غلط محتاج مراجعة.

### 4.7 التغطية الاختبارية

`Domain.UnitTests` بتغطي:
- الخمس حالات المرجعية من المواصفات
- حدود شرائح الخدمة (5 سنوات بالضبط مقابل 5 سنوات ويوم، وعدم التراكم عند 8 سنوات)
- حدود قواعد الحضور (2 / 3 / 5 / 6 / 15 / 16 يوم)
- التقريب عند نقطة المنتصف `.xx5`

## 5. البيانات المرجعية المزروعة (Seeded Data)

بتتزرع تلقائياً أول مرة النظام يشتغل على قاعدة بيانات جديدة.

### الدرجات الوظيفية — `payroll.JobGrades` (3 صفوف ثابتة)

| # | بالعربي | بالإنجليزي | الراتب الأساسي |
|---|---|---|---|
| 1 | أولى | First | 12,000.00 |
| 2 | ثانية | Second | 9,000.00 |
| 3 | ثالثة | Third | 6,500.00 |

الصفوف دي **ثابتة العدد** — تقدر تعدّل الأسماء والمرتبات، لكن مافيش إضافة أو حذف درجات من الواجهة (الـ API فيها `GET` و `PUT` بس).

### شرائح حوافز سنوات الخدمة — `payroll.ServiceIncentiveTiers`

| تجاوز (سنة) | النسبة |
|---|---|
| 5 | 5% |
| 7 | 10% |

> النسب دي **قيم مبدئية** — المواصفات حدّدت عتبات السنوات (5 و 7) بس، ومش النسب. قابلة للتعديل بالكامل من الشاشة.

### قواعد الحضور — `payroll.AttendanceRules`

| من (يوم) | إلى (يوم) | النوع | النسبة |
|---|---|---|---|
| 0 | 0 | **حافز** | 5% |
| 3 | 5 | خصم | 5% |
| 6 | 10 | خصم | 10% |
| 11 | 15 | خصم | 20% |
| 16 | ∞ | خصم | 30% |

> **انتبه للفجوة عند يوم أو يومين غياب:** مافيش قاعدة تغطّي 1–2 يوم، يعني الموظف اللي غاب يوم أو يومين مابياخدش حافز ومابيتخصمش منه حاجة. راجع [القسم 12](#12-نقاط-معروفة-ومفتوحة-للمراجعة) — فيه اختلاف بسيط عن نص المواصفات هنا يستاهل قرار منك.

### إعدادات الاحتساب — `payroll.PayrollSettings`

صف واحد فقط (مضمون بقيد `CK_PayrollSettings_SingleRow` على مستوى قاعدة البيانات)، قيمته الافتراضية: **Additive (جمعية)**.

### حساب المدير — `security.AdminUsers`

بيتزرع من الإعدادات (`AdminSeed:Username` / `AdminSeed:Password`)، **مش من migration**. لو مافيش حساب مدير والإعدادات فاضية، النظام بيرفض يقوم ويطلّع استثناء واضح. مافيش تسجيل ذاتي، ومافيش أدوار (Roles) — مستخدم واحد بصلاحية كاملة.

### بيانات تجريبية (بيئة التطوير فقط)

في بيئة `Development` فيه seeder تاني (`DevelopmentDataSeeder`) بيضيف أقسام وموظفين وغيابات تجريبية **لو جدول الموظفين فاضي**.

> ⚠️ **تحذير تشغيلي:** ده بيشتغل على أي قاعدة بيانات الـ API متصل بيها، بما فيها قاعدة بيانات فعلية على سيرفر بعيد. متشغّلش `dotnet run` (اللي بيفترض Development) وأنت متصل بقاعدة بيانات حقيقية من غير ما تتأكد الأول.

## 6. دورة حياة الشهر — سير العمل الكامل

```
┌─ إعداد لمرة واحدة ──────────────────────────────────────────┐
│  1. ضبط مرتبات الدرجات الثلاث                                │
│  2. إنشاء الأقسام + نسبة حافز كل قسم                          │
│  3. ضبط شرائح حوافز سنوات الخدمة                              │
│  4. ضبط قواعد الحضور (الحافز والخصومات)                       │
│  5. اختيار طريقة الاحتساب (جمعية / تراكمية)                    │
│  6. إدخال الموظفين                                           │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─ كل شهر ────────────────────────────────────────────────────┐
│  7. شاشة الحضور: تعليم أيام الغياب طوال الشهر                  │
│  8. شاشة المسير: "توليد" لشهر معيّن  →  يُنشأ كـ مسودة         │
│  9. مراجعة التفاصيل + تفصيل راتب كل موظف                      │
│ 10. لو فيه غلط: عدّل الإعدادات أو الغياب ثم "أعد التوليد"      │
│ 11. "اعتماد"  →  المسير يتقفل نهائياً                          │
│ 12. طباعة/عرض التقارير الأربعة                                │
└─────────────────────────────────────────────────────────────┘
```

### حالتا المسير

| الحالة | المعنى | المسموح |
|---|---|---|
| **مسودة (Draft)** | مُولَّد وقابل للتعديل | إعادة التوليد، الاعتماد، تعديل غيابات الشهر |
| **معتمد (Approved)** | نهائي ومقفول | العرض والتقارير فقط |

### إيه اللي بيتقفل بالضبط بعد الاعتماد

1. **مسير الشهر نفسه**: محاولة إعادة توليد نفس الشهر ترجع `409 Conflict`. محاولة اعتماده تاني برضه `409`.
2. **غيابات الشهر**: أي إضافة أو حذف لغياب في شهر مسيره معتمد ترجع `409`، والشبكة نفسها بتظهر بعلامة "مقفول" وأزرار الحفظ متعطّلة.

القفل بيتحقق من الشهر **اللي التاريخ بتاعه فيه** — مش من المسير اللي إنت فاتحه. يعني لو حفظت دفعة غيابات فيها تواريخ من شهرين مختلفين وواحد منهم معتمد، الدفعة كلها بتترفض.

## 7. شرح كل شاشة بالتفصيل

الهيكل العام: شريط جانبي فيه ثلاث مجموعات (الرئيسية / الإعدادات / التقارير)، وشريط علوي فيه اسم المستخدم، زرار تبديل اللغة (AR/EN)، وزرار تسجيل الخروج.

---

### 7.1 شاشة تسجيل الدخول — `/login`

**وظيفتها:** الباب الوحيد للنظام. الشاشة الوحيدة اللي مش محمية بالـ Guard.

**اللي عليها:** اسم المستخدم، كلمة المرور (مع زرار إظهار/إخفاء)، زرار دخول، ورسالة خطأ مباشرة تحت النموذج.

**اللي بيحصل ورا الكواليس:**
1. `POST /api/auth/login` مع `withCredentials`
2. لو نجح: الـ Access Token بيتخزّن **في ذاكرة المتصفح فقط** (Angular signal) — **مش** في `localStorage` ولا `sessionStorage`
3. الـ Refresh Token بيرجع في **كوكي httpOnly** — الجافاسكريبت مايقدرش يقراه أصلاً
4. تحويل لـ `/dashboard`

**قواعد وحدود:**
- تحقق الواجهة: الحقلين مطلوبين
- **تحديد معدل: 5 محاولات دخول في الدقيقة** لكل عميل (الـ API بيرجع `429` بعدها)
- بيانات دخول غلط بتدي رسالة عامة — من غير تمييز بين "المستخدم غير موجود" و"كلمة مرور خاطئة"

**ليه الـ Access Token في الذاكرة بس؟** عشان لو حد نجح في حقن سكريبت في الصفحة (XSS) مايقدرش يسرق توكن دائم. ولو المستخدم عمل Refresh للصفحة، النظام بيحاول يسترجع الجلسة تلقائياً عن طريق كوكي الـ Refresh.

---

### 7.2 لوحة التحكم — `/dashboard`

**وظيفتها:** نظرة سريعة على حالة النظام أول ما تدخل. مافيش أي إجراءات — عرض فقط.

**ثلاث بطاقات مؤشرات:**

| المؤشر | مصدره |
|---|---|
| عدد الموظفين النشطين | إجمالي عدد الموظفين غير المحذوفين |
| إجمالي آخر مسير معتمد | صافي رواتب آخر مسير حالته "معتمد" + الشهر بتاعه |
| أيام الغياب هذا الشهر | مجموع أيام الغياب لكل الموظفين في الشهر الحالي |

**رسم بياني:** أعمدة بتوضّح **صافي الرواتب مجمّعاً حسب القسم** لآخر مسير معتمد.

**حالات فارغة:** لو مافيش أي مسير معتمد لسه، البطاقة بتعرض "—" والرسم البياني بيعرض رسالة "لا يوجد مسير معتمد".

**ملاحظة تقنية:** الشاشة بتجيب آخر 12 مسير وبتدوّر فيهم على أول واحد معتمد (القائمة مرتبة تنازلياً بالسنة والشهر). فلو عندك أكتر من 12 مسير مسودة متتالية من غير اعتماد، المؤشر ممكن ما يلاقيش المسير المعتمد القديم.

---

### 7.3 الموظفون — `/employees`

**وظيفتها:** القائمة الرئيسية لكل الموظفين، ونقطة الدخول للإضافة والتعديل والحذف.

**الفلاتر:** بحث نصي + فلتر قسم + فلتر درجة وظيفية.

**الأعمدة:** الاسم، البريد الإلكتروني، الهاتف، القسم، الدرجة، تاريخ التعيين + عمود إجراءات (تعديل / حذف).

**الترقيم:** 20 صف في الصفحة، والفلاتر والترقيم بيتنفّذوا على السيرفر (مش في المتصفح) — فالجدول بيفضل سريع مهما كبر عدد الموظفين.

**الحذف:** بيطلب تأكيد باسم الموظف، وبيعمل **حذف منطقي (Soft Delete)** — الصف بيتعلّم `IsDeleted = true` ومابيتشالش من قاعدة البيانات. ليه؟ عشان مسيرات الشهور القديمة اللي الموظف كان فيها تفضل سليمة ومفهومة.

**نقطة مهمة:** الموظف المحذوف بيختفي من الشاشات والمسيرات الجاية، لكن اسمه بيفضل ظاهر في التقارير والمسيرات القديمة (بفضل مبدأ اللقطة).

---

### 7.4 نموذج موظف (إضافة/تعديل) — `/employees/new` و `/employees/:id`

**وظيفتها:** إدخال أو تعديل بيانات موظف واحد. نفس الشاشة بتخدم الحالتين؛ لو فيه `id` في المسار بتشتغل وضع تعديل.

**الحقول** (مطابقة لما هو مطلوب في المواصفات بالضبط):

| الحقل | النوع | قواعد التحقق |
|---|---|---|
| الاسم | نص | مطلوب، حتى 150 حرف |
| تاريخ الميلاد | تاريخ | مطلوب |
| العنوان | نص | مطلوب، حتى 250 حرف |
| رقم الهاتف | نص | مطلوب، حتى 20 حرف |
| البريد الإلكتروني | نص | مطلوب، صيغة بريد صحيحة، حتى 150 حرف، **فريد بين الموظفين النشطين** |
| الدرجة الوظيفية | قائمة | مطلوب، لازم تكون درجة موجودة |
| القسم التابع له | قائمة | مطلوب، لازم يكون قسم موجود |
| تاريخ التعيين | تاريخ | مطلوب |

**قواعد منطقية بين الحقول (بتتحقق على السيرفر):**
- تاريخ التعيين **لا يكون في المستقبل**
- تاريخ التعيين **بعد** تاريخ الميلاد
- عمر الموظف عند التعيين **18 سنة على الأقل**

**التعامل مع الأخطاء:** التحقق بيتم على السيرفر بـ FluentValidation، والأخطاء بترجع مفهرسة باسم الحقل وبتظهر تحت الحقل المعني مباشرة — مش كرسالة عامة في الأعلى. والرسايل بتيجي بلغة الواجهة الحالية (الواجهة بتبعت `Accept-Language` مع كل نداء).

**تكرار البريد الإلكتروني** بيرجع `409 Conflict` برسالة مخصصة.

---

### 7.5 الأقسام — `/departments`

**وظيفتها:** إدارة أقسام الشركة ونسبة الحافز المرتبطة بكل قسم. الشاشة دي بتغطي بندين من المواصفات مع بعض: **إدارة الأقسام** و**حوافز القسم**.

**الأعمدة:** اسم القسم، نسبة الحافز (معروضة بعلامة %) + إجراءات.

**الإضافة/التعديل:** نافذة منبثقة (Dialog) صغيرة فيها حقلين بس:
- الاسم — مطلوب، حتى 100 حرف، **فريد** (بدون حساسية لحالة الأحرف)
- نسبة الحافز — من 0 إلى 100

**الحذف — وده أهم جزء في الشاشة:**

الحذف **مرفوض** لو القسم لسه فيه موظفين نشطين، وبيرجع `409 Conflict` برسالة واضحة. لازم تنقل الموظفين لقسم تاني (أو تحذفهم) الأول.

ليه؟ عشان الموظف لازم يكون تابع لقسم عشان يتحسب راتبه. لو سمحنا بحذف قسم فيه موظفين، توليد المسير الشهر الجاي كان هيسقطهم بصمت.

لو عدّى الفحص، الحذف بيبقى **منطقي (Soft Delete)** برضه.

> ملاحظة دقيقة: الموظفون المحذوفون منطقياً **لا** يمنعون حذف القسم — الفحص بيشوف الموظفين النشطين بس.

**أثر تعديل نسبة الحافز:** بيأثر على المسيرات اللي **هتتولّد بعد التعديل** فقط.

---

### 7.6 الحضور والانصراف — `/attendance`

**وظيفتها:** الشاشة الأكثر استخداماً شهرياً. تسجيل أيام الغياب لكل الموظفين في شبكة تقويمية واحدة.

**شكلها:** جدول فيه:
- عمود مثبّت على الجانب: اسم الموظف
- عمود لكل يوم في الشهر (28/29/30/31 حسب الشهر — بيتحسب تلقائياً)
- كل خلية مربع صغير: **أحمر = غائب**، **فاضي = حاضر**

**الفلاتر أعلى الشاشة:** السنة (السنة الماضية / الحالية / القادمة)، الشهر (1–12)، القسم.

**طريقة العمل:**
1. اضغط على أي خلية → بتتبدّل بين غائب/حاضر **محلياً فقط** (لسه محصلش حفظ)
2. عدّاد "تغييرات غير محفوظة (ن)" بيظهر فوق
3. **حفظ** → بيبعت الفروقات بس (`add` و `remove`) في نداء واحد
4. **تجاهل** → بيرجّع الشبكة لآخر حالة محفوظة

**ليه التصميم ده؟** عشان تعليم 30 يوم × 50 موظف بنداء لكل ضغطة يعني مئات النداءات. النظام بيجمّع كل التغييرات ويبعتهم دفعة واحدة، وبيبعت الفرق بس مش كل الحالة.

**قواعد التحقق عند الحفظ (على السيرفر):**

| القاعدة | النتيجة لو اتخالفت |
|---|---|
| الموظف موجود | `404` |
| التاريخ **ليس في المستقبل** | `400` |
| التاريخ **بعد تاريخ تعيين الموظف** | `400` |
| مسير الشهر **غير معتمد** | `409` |

الفحص بيتم على **كل الإدخالات قبل حفظ أي حاجة** — يعني الدفعة إما تنجح كلها أو تفشل كلها، مافيش حفظ جزئي.

**الحفظ آمن للتكرار (Idempotent):** لو بعتّ إضافة ليوم متسجّل أصلاً، بيتجاهله من غير خطأ. ولو بعتّ حذف ليوم مش متسجّل، بيتجاهله برضه.

**القفل:** لو مسير الشهر معتمد، بتظهر شارة "مقفول" جنب عنوان الشاشة، وزرار الحفظ بيتعطّل، والضغط على الخلايا مابيعملش حاجة.

---

### 7.7 مسيرات الرواتب — `/payroll`

**وظيفتها:** قائمة بكل المسيرات الشهرية + نقطة توليد مسير جديد.

**الأعمدة:** الفترة (`YYYY-MM`)، الحالة (شارة ملوّنة: مسودة / معتمد)، عدد الموظفين، إجمالي صافي الرواتب + زرار عرض.

**التوليد:** قائمتين (سنة + شهر) وزرار "توليد". بعد النجاح بيحوّلك تلقائياً على شاشة تفاصيل المسير.

**قواعد التوليد — بالترتيب اللي بتتحقق بيه:**

| # | الفحص | النتيجة لو فشل |
|---|---|---|
| 1 | الشهر بين 1 و 12 | `400` |
| 2 | الفترة **ليست في المستقبل** | `400` |
| 3 | مافيش مسير **معتمد** لنفس الشهر | `409` |
| 4 | فيه موظف مؤهّل واحد على الأقل | `400` |

**مين "الموظف المؤهّل"؟** أي موظف نشط **تاريخ تعيينه ≤ آخر يوم في الشهر**. يعني موظف اتعيّن في 20 مارس بيدخل في مسير مارس.

> **مافيش احتساب نسبي (Proration) للتعيينات وسط الشهر** — الموظف اللي اتعيّن يوم 28 من الشهر بياخد راتب الشهر كامل. ده قرار مُتّخذ ومعلن، لو محتاج تغييره فده تعديل في `PayrollRunService`.

**إعادة التوليد:** لو المسير موجود وحالته **مسودة**، النظام:
1. بيمسح كل صفوف `PayrollItems` القديمة بتاعة المسير
2. بيحدّث طريقة الاحتساب وتاريخ التوليد
3. بيعيد إنشاء كل الصفوف بالإعدادات والغيابات الحالية

فلو عدّلت غياب أو نسبة حافز، أعد التوليد والأرقام هتتحدّث. **نفس رقم المسير بيتحافظ عليه** — مابيتعملش مسير جديد.

---

### 7.8 تفاصيل المسير — `/payroll/:id`

**وظيفتها:** مراجعة مسير شهر كامل قبل اعتماده، والاطّلاع على تفصيل راتب أي موظف.

**ست بطاقات مؤشرات في الأعلى:**
1. الفترة + شارة الحالة
2. عدد الموظفين
3. **إجمالي صافي الرواتب**
4. إجمالي حوافز الأقسام
5. إجمالي حوافز الخدمة
6. **إجمالي تسويات الحضور** (رقم صافي — الحوافز ناقص الخصومات)

المؤشرات دي محسوبة بـ `SUM` على مستوى قاعدة البيانات مباشرة، مش في الذاكرة.

**زرار الاعتماد:** بيظهر فقط لو الحالة "مسودة"، وبيطلب تأكيد بنافذة منبثقة مع تنبيه إن الإجراء نهائي.

**جدول بنود المسير:**
- بحث باسم الموظف + فلتر قسم، 20 صف في الصفحة
- الأعمدة: الموظف، القسم، الدرجة، الراتب الأساسي، صافي الراتب + زرار "التفصيل"

**نافذة تفصيل الراتب (الأهم للمراجعة):** بتعرض حساب الموظف سطر بسطر:

```
الراتب الأساسي                            10,000.00
حافز القسم (10%)                           1,000.00
حافز الخدمة (5% — 6 سنوات)                   500.00
خصم الحضور (5% — 4 أيام غياب)                −500.00
──────────────────────────────────────────────────
صافي الراتب                               11,000.00
```

كل سطر بيعرض **النسبة المستخدمة والسبب** — عدد سنوات الخدمة، وعدد أيام الغياب. ده بيخلي مراجعة أي راتب مشكوك فيه تتم في ثانية من غير رجوع للإعدادات.

لو الموظف مالوش تسوية حضور (غاب يوم أو يومين مثلاً)، السطر بيظهر بـ "لا يوجد".

---

### 7.9 الإعدادات ← المرتبات — `/settings/salaries`

**وظيفتها:** تحديد الراتب الأساسي لكل درجة وظيفية. ده اللي بيقابل بند **"إدارة المرتبات"** في المواصفات.

**شكلها:** جدول من ثلاثة صفوف بس (أولى/ثانية/ثالثة)، **قابل للتعديل داخل الخلية مباشرة**.

**طريقة العمل:** دبل كليك (أو Enter) على أي خلية → عدّل → اخرج من الخلية → **الحفظ بيتم تلقائياً فوراً** وبتظهر رسالة نجاح. مافيش زرار حفظ.

**الأعمدة القابلة للتعديل:** الاسم بالإنجليزي، الاسم بالعربي، الراتب الأساسي (محرّر أرقام بخانتين عشريتين وحد أدنى صفر).

**قواعد التحقق:** الأسماء مطلوبة وحتى 50 حرف، الراتب الأساسي **أكبر من صفر**.

**مافيش إضافة ولا حذف** — الدرجات الثلاث ثابتة بالتصميم، مطابقة للمواصفات.

**لو فشل الحفظ**، الجدول بيعيد تحميل نفسه من السيرفر عشان ما يفضلش عارض قيمة متغيرة مش متخزّنة.

---

### 7.10 الإعدادات ← حوافز الخدمة — `/settings/service-incentives`

**وظيفتها:** إدارة شرائح "حوافز على عدد سنوات العمل" من المواصفات.

**الأعمدة:** "تجاوز (سنة)"، النسبة % + إجراءات (تعديل / حذف).

**الإضافة/التعديل:** نافذة منبثقة بحقلين:
- تجاوز (سنة) — عدد صحيح ≥ 0، **فريد** (فيه فهرس فريد على مستوى قاعدة البيانات)
- النسبة — من 0 إلى 100

القائمة بتتعرض مرتبة تصاعدياً بعدد السنوات.

**اللي لازم تفهمه هنا:** الشرائح **لا تتراكم**. لو عندك شريحة 5 سنوات بـ 5% وشريحة 7 سنوات بـ 10%، الموظف اللي عنده 9 سنوات بياخد **10% فقط** — مش 15%. فلما تضبط النسب، اعتبرها نسباً **نهائية** مش إضافية.

تقدر تضيف شرائح جديدة (10 سنوات، 15 سنة… إلخ) — مش مقيّد بالاتنين المزروعين.

---

### 7.11 الإعدادات ← قواعد الحضور — `/settings/attendance-rules`

**وظيفتها:** تعريف أثر أيام الغياب على الراتب — الجزء اللي بيغطي بند **"إدارة الحضور والانصراف"** من ناحية النسب.

**الأعمدة:** من (يوم)، إلى (يوم — فاضي معناها "بلا حد أعلى")، النوع (شارة: حافز / خصم)، النسبة % + إجراءات.

**الإضافة/التعديل:** نافذة منبثقة بأربعة حقول:
- من (يوم) — عدد صحيح
- إلى (يوم) — **اختياري**؛ سيبه فاضي عشان تعمل قاعدة مفتوحة (مثلاً "16 يوم فأكثر")
- النوع — حافز أو خصم
- النسبة — من 0 إلى 100

**قواعد التحقق:** `إلى` لازم تكون فاضية أو **أكبر من أو تساوي** `من`.

**تحذير مهم — النظام مابيمنعش التداخل أو الفجوات:**

مافيش تحقق يمنعك تعمل قاعدتين متداخلتين (مثلاً 3–5 و 4–8). لو حصل تداخل، **أول قاعدة مطابقة بترتيب الاسترجاع بتفوز** — وده سلوك غير مضمون الترتيب. برضه لو سبت فجوة (زي الفجوة الموجودة حالياً عند 1–2 يوم)، الأيام دي مالهاش أثر خالص.

خلي بالك إن **الحافز والخصم كلاهما مُعرَّفان هنا** — الصف الأول (0 يوم غياب) نوعه "حافز"، وده اللي بيحقّق طلب المواصفات: "يوم أو لا يوجد → حافز وليس خصم، بنسبة يقوم المدير بوضعها وتعديلها".

---

### 7.12 الإعدادات ← طريقة الاحتساب — `/settings/calculation`

**وظيفتها:** اختيار الطريقة الحسابية اللي هتُستخدم في توليد المسيرات.

**شكلها:** بطاقتان قابلتان للاختيار — "جمعية" و"تراكمية" — كل واحدة تحتها **مثال حي محسوب** بنفس الأرقام (أساسي 10,000، قسم 10%، خدمة 5%، حضور −5%) عشان تشوف الفرق بعينك قبل ما تقرّر.

**زرار حفظ** بيثبّت الاختيار.

**نقطتان حاسمتان:**
1. **الاختيار بيأثر على المسيرات اللي هتتولّد بعد الحفظ فقط.** المسيرات الموجودة (حتى المسودة) مابتتغيرش لحد ما تعيد توليدها.
2. **الطريقة بتتسجّل داخل كل مسير** في عمود `CalculationMode`، فتقدر تعرف أي مسير قديم اتحسب بأي طريقة.

**ملاحظة تقنية:** المثال المعروض في الشاشة محسوب في الواجهة (JavaScript) للتوضيح البصري فقط. **المرجع الحقيقي هو `PayrollCalculator` في الباك إند** — أي اختلاف في الخانة العشرية بين المثال والمسير الفعلي، الصح هو الباك إند.

### 7.13 التقارير — أربع شاشات

كل شاشات التقارير ليها نفس البنية: شريط فلاتر + جدول + **زرار طباعة**. الطباعة بتستخدم طباعة المتصفح مع معالجة خاصة تخلي الجدول يتطبع كامل (كل الصفوف) بدل الجزء الظاهر على الشاشة فقط.

#### (1) تقرير الحضور والانصراف — `/reports/attendance`

- **الفلاتر:** سنة، شهر، قسم
- **الأعمدة:** الموظف، القسم، **عدد أيام الغياب**
- **مصدر البيانات:** جدول الغيابات **مباشرة (بيانات حية)** — مش من مسير
- **الفايدة:** تقدر تشوف الحضور لأي شهر **حتى لو مسيره لسه ما اتولّدش** — فهو أداة متابعة يومية مش تقرير نهائي بس
- الموظفون اللي مالهمش غياب بيظهروا بصفر

#### (2) تقرير الحوافز والخصومات — `/reports/incentives`

- **الفلاتر:** **المسير** (قائمة بآخر 24 مسير)، قسم
- **الأعمدة:** الموظف، القسم، حافز القسم، حافز الخدمة، تسوية الحضور، صافي الراتب
- **مصدر البيانات:** لقطة `PayrollItems` بتاعة المسير المختار
- **الفايدة:** ده تقرير "التفكيك" — بيوضّح كل موظف أخد كام من كل بند بالضبط. مفيد للردّ على استفسارات الموظفين
- بيختار أحدث مسير تلقائياً أول ما تفتح الشاشة

#### (3) تقرير العاملين بالشركة — `/reports/employees`

- **الفلاتر:** قسم، درجة وظيفية
- **الأعمدة:** الاسم، البريد الإلكتروني، القسم، الدرجة، تاريخ التعيين
- **مصدر البيانات:** بيانات الموظفين الحالية **(حية، مش مرتبطة بمسير)**
- **الفايدة:** كشف شامل بالقوة العاملة — للموارد البشرية والتوزيع التنظيمي

#### (4) تقرير مرتبات العاملين — `/reports/salaries`

- **الفلاتر:** المسير، قسم
- **الأعمدة:** الموظف، القسم، **الراتب الأساسي**، **صافي الراتب**
- **مصدر البيانات:** لقطة المسير المختار
- **الفايدة:** الكشف المختصر اللي بيتسلّم للمالية/البنك — الأساسي والصافي وبس

**ملخص الفرق:**

| التقرير | مربوط بمسير؟ | بيقرأ من |
|---|---|---|
| الحضور | ❌ لا | جدول الغيابات (حي) |
| العاملين | ❌ لا | جدول الموظفين (حي) |
| الحوافز والخصومات | ✔ نعم | لقطة `PayrollItems` |
| المرتبات | ✔ نعم | لقطة `PayrollItems` |

## 8. الأمان وإدارة الجلسة

### نموذج المستخدمين

**مستخدم إداري واحد، بلا تسجيل ذاتي، وبلا أدوار.** كل شيء محمي بـ `[Authorize]` ما عدا `login` و `refresh`. مافيش صلاحيات دقيقة — اللي بيدخل عنده كل حاجة.

### آلية التوكن

```
تسجيل الدخول
    ├─ Access Token (JWT)  — صلاحيته 15 دقيقة — يُحفظ في ذاكرة المتصفح فقط
    └─ Refresh Token       — صلاحيته 7 أيام  — كوكي httpOnly + Secure + SameSite=Strict
                                              — Path = /api/auth
```

**قواعد الحماية المطبّقة:**

1. **الـ Refresh Token مايوصلش للجافاسكريبت أبداً** — لا في جسم الاستجابة ولا في التخزين المحلي. كوكي httpOnly بس.
2. **تُخزَّن في قاعدة البيانات كـ SHA-256 hash فقط** — لو حد سرب الداتابيز مايقدرش يستخدم التوكنات.
3. **تدوير عند كل استخدام** — كل مرة تجدّد، بيتلغي التوكن القديم وينزل واحد جديد.
4. **كشف إعادة الاستخدام** — لو حد حاول يستخدم توكن اتدوّر قبل كده، النظام **بيلغي سلسلة التوكنات كلها** للمدير ده ويجبره يدخل من جديد. ده دفاع ضد سرقة التوكن.
5. **تحديد معدل:** 5 محاولات دخول/دقيقة، و300 نداء/دقيقة عام (نافذة منزلقة).

### التدفق التلقائي عند انتهاء الصلاحية

```
نداء API  →  401
    ↓
الـ Interceptor يوقف النداء ويطلب تجديد (نداء واحد فقط حتى لو 10 نداءات فشلت معاً)
    ↓
نجح؟  →  يعيد النداء الأصلي بالتوكن الجديد  (المستخدم ما حسّش بحاجة)
فشل؟  →  تُمسح الجلسة  →  تحويل لشاشة الدخول
```

### الصلاحيات الأخرى

- تشفير كلمات المرور بخدمة `PasswordHashing` مخصصة
- كل الأسرار (سلسلة الاتصال، مفتاح JWT، بيانات المدير) خارج الكود المصدري
- رؤوس Correlation ID على كل طلب لتتبّع الأخطاء في الـ Logs
- معالج أخطاء عام (`GlobalExceptionHandler`) بيمنع تسرّب تفاصيل الاستثناءات الداخلية للعميل

### الحذف المنطقي (Soft Delete)

`Employees` و `Departments` عليهم **فلتر استعلام عام (Global Query Filter)** على مستوى EF Core — يعني أي استعلام في النظام بيستثني المحذوفين تلقائياً من غير ما الكود يفتكر يعمل كده. ده بيمنع فئة كاملة من الأخطاء (نسيان `WHERE IsDeleted = 0`).

### تتبّع التغييرات (Auditing)

كل الجداول الرئيسية بتطبّق `IAuditable`: `CreatedAt`, `CreatedBy`, `LastModifiedAt`, `LastModifiedBy` — بتتعبّى تلقائياً في `SaveChanges`.

### التخزين المؤقت (Caching)

النظام بيستخدم `IMemoryCache` لـ:
- القوائم المرقّمة (موظفين، أقسام، مسيرات) — بمفتاح مركّب من كل الفلاتر
- قائمة الأقسام المختصرة (Lookup)
- الشرائح والقواعد الخام (بتُقرأ في كل توليد مسير)

**والإبطال دقيق:** مثلاً تعديل اسم قسم بيبطّل **كاش الموظفين كمان** — لأن اسم القسم مُدمج داخل صفوف قائمة الموظفين.

## 12. نقاط معروفة ومفتوحة للمراجعة

القسم ده أمانة توثيقية — مش عيوب مخفية، ده اللي محتاج قرار منك أو معرفة قبل التسليم.

### 12.1 ⚠ غياب يوم واحد لا يحصل على الحافز (اختلاف عن المواصفات)

المواصفات بتقول: **"يوم أو لا يوجد → حافز وليس خصم"**. التنفيذ الحالي بيدي الحافز عند **صفر يوم غياب فقط**. الموظف اللي غاب يوم واحد (أو يومين) مابياخدش حافز ومابيتخصمش منه.

**الإصلاح بسيط ومن غير كود:** من شاشة `/settings/attendance-rules`، عدّل الصف الأول من `من 0 إلى 0` لـ `من 0 إلى 1` (لو "يوم أو لا يوجد" معناها 0 أو 1). لو معناها 0 إلى 2، خليها `من 0 إلى 2`.

**قرار مطلوب منك:** هل "يوم أو لا يوجد" تعني 0–1 يوم، ولا هي مقصودة كفجوة؟ لأن التنفيذ الحالي بيسيب فجوة عند 1–2 يوم بلا أي أثر.

### 12.2 مسارات PDF غير موصولة بالواجهة

الباك إند فيه أربع نقاط نهاية PDF شغّالة بـ RDLC (`/api/reports/*/pdf`) مع ملفات `.rdlc` جاهزة، لكن شاشات التقارير في الواجهة بتستخدم `window.print()` بس. توصيلها شغل صغير: زرار إضافي بيفتح رابط الـ PDF.

### 12.3 لا يوجد منع للتداخل في قواعد الحضور

تقدر تحفظ قاعدتين متداخلتين (3–5 و 4–8) والنظام مش هيحذّرك. لو حصل تداخل، أول قاعدة مطابقة بترتيب الاسترجاع هي اللي بتتطبّق — وده ترتيب غير مضمون. **يُفضَّل مراجعة القواعد بصرياً بعد أي تعديل.**

### 12.4 لا يوجد تحكّم بالتزامن (Optimistic Concurrency)

مافيش أعمدة `rowversion` على جداول الإعدادات ولا الموظفين. لو (نظرياً) اتنين فتحوا نفس السجل وحفظوا، آخر واحد بيحفظ بيكسب بصمت. عملياً النظام مستخدم إداري واحد، فالخطر محدود.

### 12.5 إعدادات CORS مفتوحة بالكامل

الـ API مضبوط على قبول **أي أصل (origin)** مع `AllowCredentials`. ده اتعمل **بناءً على طلبك الصريح** عشان الـ API يكون متاح لأي مستهلك.

**اللي لازم تعرفه:** في الوضع ده، أي موقع خارجي يقدر يبعت طلبات حاملة للكوكي نيابة عن مستخدم مسجّل دخوله — يعني CORS ما بقاش بيوفّر حماية ضد CSRF هنا. كوكي `SameSite=Strict` بيقلّل الخطر كتير، لكن لو النظام هيتنشر على الإنترنت العام يُفضَّل مراجعة القرار ده أو إضافة CSRF token.

### 12.6 الحذف المنطقي وأثره على التقارير

الموظف المحذوف منطقياً:
- بيختفي من كل الشاشات والمسيرات الجديدة
- بيفضل ظاهر في المسيرات والتقارير القديمة (مقصود — مبدأ اللقطة)
- **غياباته بتفضل في قاعدة البيانات** لكن مش هتظهر في شبكة الحضور (لأن الشبكة بتبني صفوفها من الموظفين النشطين)

### 12.7 ملاحظة تشغيلية: الـ Seeder التجريبي

`DevelopmentDataSeeder` بيشتغل تلقائياً في بيئة Development لو جدول الموظفين فاضي، وبيضيف أقسام وموظفين وغيابات وهمية — **على أي قاعدة بيانات الـ API متصل بيها**. حصل فعلاً إنه أضاف بيانات تجريبية على قاعدة بيانات بعيدة. **تأكد من بيئة التشغيل وسلسلة الاتصال قبل أول `dotnet run`.**

### 12.8 حالة التحقق النهائي

- ✔ المشروعان يُبنيان بنجاح بلا أخطاء
- ✔ مجموعة الاختبارات الخلفية كاملة تمر (Domain / Application / Infrastructure / API)
- ✔ خادم Angular التطويري يعمل ويقدّم صفحات صحيحة
- ❌ **لم يتم اختبار المسار الكامل** (دخول ← إنشاء موظف ← تعليم غياب ← توليد ← اعتماد) في متصفح حقيقي على قاعدة بيانات حية

ده أول حاجة تتعمل قبل التسليم النهائي.

### 12.9 ملاحظات تتعلق بالمستودع

- `README.md` بيقول إن نصوص الواجهة إنجليزية فقط — **ده قديم**؛ الواجهة دلوقتي ثنائية اللغة بالكامل والعربي هو الافتراضي (ملفا `public/i18n/ar.json` و `en.json` متطابقان في المفاتيح)
- مجلد `PayRollAngular/` غير مستخدم إطلاقاً وآمن حذفه
- `payroll-web` **مش مستودع Git لسه** — الشغل فيه غير متتبّع لحد ما تعمل `git init`

## 13. تشغيل النظام محلياً

### الباك إند

```bash
cd PayRollApi

# إعداد الأسرار (مرة واحدة)
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "<سلسلة الاتصال>" -p PayRollApi/PayRollApi.csproj
dotnet user-secrets set "Jwt:Key" "<مفتاح عشوائي 32 حرف على الأقل>" -p PayRollApi/PayRollApi.csproj
dotnet user-secrets set "AdminSeed:Username" "admin" -p PayRollApi/PayRollApi.csproj
dotnet user-secrets set "AdminSeed:Password" "<كلمة مرور قوية>" -p PayRollApi/PayRollApi.csproj

# تطبيق الـ migrations
dotnet ef database update --project Infrastructure --startup-project PayRollApi

# التشغيل
dotnet run --project PayRollApi
```

Swagger على: `https://localhost:7290/swagger`

> ⚠ **أدوات EF لا تقرأ `appsettings.json`** — ملف `DesignTimeDbContextFactory.cs` فيه سلسلة اتصال ثابتة لقاعدة بيانات وهمية (`PayRollDB_DesignTimeOnly`) عشان `migrations add` ما يشغّلش `Program.cs`. عشان كده `dotnet ef database update` **لازم** تديله قاعدة البيانات الحقيقية صراحةً:
> ```bash
> dotnet ef database update --project Infrastructure --startup-project PayRollApi --connection "<سلسلة الاتصال الحقيقية>"
> ```
> من غير كده هيفشل بخطأ Named Pipes / error 40 وهو بيحاول يتصل بـ localhost.

### الواجهة

```bash
cd ../payroll-web
npm install
npm start          # http://localhost:4200
```

الـ proxy مضبوط في `proxy.conf.json` ليوجّه `/api` إلى `https://localhost:7290` — **لا تعطّله** (اقرأ [القسم 2](#2-المعمارية-والتقنيات)).

### البناء والاختبار

```bash
dotnet build PayRollApi.slnx
dotnet test  PayRollApi.slnx

cd payroll-web && npm run build
```
